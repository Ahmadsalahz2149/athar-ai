# ADRs (v4)

Each: context · options · decision · consequences.

**ADR-000 Phase −1 first.** *Context:* the plan put 63 dev-days ahead of any paying signal. *Decision:* **Wizard-of-Oz concierge for 2 agencies (text-only, manual prompts) before any product; a paying agency gates all of M0+.** *Consequences:* WTP is tested in ~1 week for 0 dev-days; if it fails, no code is written.

**ADR-001 Billing: concierge-first, Paddle deferred.** *Context:* MVP sells to ~5 agencies by manual invoice; Paddle needs a live site + legal pages + review latency and isn't required to hand-invoice 5 customers. *Decision:* **No self-serve billing in MVP.** Keep `PaymentProvider` interface (empty adapters) + `credit_ledger` (cost control) + Terms/Privacy/refund. **Paddle (MoR, carries KSA 15% VAT) + Stripe stub build *after* Design Partners validate WTP.** *Consequences:* the longest external dependency is removed from the critical path; billing is a bank transfer + PDF until validated.

**ADR-002 Transcription** — decided by the M0.5 bake-off on 10 real samples (WER/CER + dialect preservation + latency + $/hr → `EVAL_TRANSCRIPTION.md`); adapter in `lib/ai/transcription.ts`; **not on the Phase −1 path** (text-only). *Consequences:* provider swappable via env; evidence-based (ElevenLabs Scribe is a strong candidate the founder already has).

**ADR-003 Retrieval** — pgvector + Arabic semantic chunking (overlap, page/timestamp citations) + hybrid (vector + FTS/trigram); DNA reads a stratified sample; lexical mechanism finalized in M3. *Consequences:* bounded near-linear cost; citations; more M3 build than naive stuffing.

**ADR-004 Model tiering** — Haiku 4.5 classify/extract · Sonnet 5 drafts/variants · Opus 4.8 DNA synthesis + polish; prompt caching on the stable prefix; Batch API for nightly bulk; **all model IDs centralized in `lib/ai/models.ts`** (fix). *Consequences:* per-op cost predictable and low; plans priced in credits, not files; no scattered model names.

**ADR-005 Tenancy enforcement** — Drizzle's pooled service credential bypasses RLS, so "RLS protects users" is an illusion. *Decision:* **mandatory `db.forOrg()` façade + lint rule + RLS backstop**, validated by a **CI tenancy test** (2-brand org). *Consequences:* one code path for tenant data; the lint rule + test are load-bearing and must never be disabled.

**ADR-006 Framework** — **Next.js App Router + TS** (one codebase, locale routing, route handlers/server actions, middleware, Vercel). *Consequences:* fastest path; the client-heavy prototype maps to server components + islands.

**ADR-007 Cold start** — TTFV must be <5 min. *Decision:* **DNA v0 from a 10-question voice interview OR pasted posts / a public URL** — no upload required — shipped in the MVP. *Consequences:* first draft reachable in minutes; extra M2 build, but the largest de-risking lever.

**ADR-008 Embedding model (C4).** *Context:* changing the embedding model later forces a full re-embed. *Options:* pin by price (rejected) · **pin by an Arabic recall@5 eval**. *Decision:* M0.5 runs 20 Arabic queries × a 3-source corpus, recall@5 across ≥2 models (`EVAL_RETRIEVAL.md`); `vector(N)` pinned only after. *Consequences:* a one-time eval buys the right dimension and avoids a costly re-embed.

**ADR-009 Media retention (fix).** *Context:* deleting originals kills click-a-quote-to-hear-the-moment; keeping raw originals inflates COGS to ~$20/brand/mo. *Decision:* **transcode to 24 kbps mono Opus (~20 MB / 2-hr podcast), keep permanently, delete the original.** *Consequences:* ~$6 COGS retained *and* the audio-citation feature survives (chunks cite Opus timestamps).

**ADR-010 Contractor acceptance (fix).** *Decision:* **the acceptance harness (CI tenancy test, prompt-injection eval, SSRF eval, credit-math unit tests) is founder-authored and exists before any commodity work is delegated; acceptance = CI green, never code-judgment.** *Consequences:* safe delegation of the ~43 commodity dev-days.

**ADR-011 Row-level security (the ADR-005 backstop, delivered).** *Context:* ADR-005 kept tenant data behind the `forOrg()` façade and promised RLS as a backstop; the backstop was never built, so isolation rested entirely on developers remembering the façade — and, as ADR-005 itself noted, RLS is an illusion while the app connects as the table owner, which Postgres exempts from its own policies. *Options:* leave it at the façade (rejected — one forgotten `WHERE org_id` is a cross-tenant leak) · a second owner connection for system work (rejected — doubles the pooled connections on Supabase for no extra protection against the actual threat) · **policies keyed on transaction-local settings, enforced by connecting as an unprivileged role.** *Decision:* **every tenant table gets `ENABLE ROW LEVEL SECURITY` and a deny-by-default policy `org_id = current_setting('app.org_id')`; `forOrg()` sets that setting per transaction; the ~8 genuinely cross-org components opt out explicitly through `asSystem()`.** Enabled but **not** `FORCE`d: the policies are dormant for the owning role, so applying the migration changes nothing, and enforcement is turned on by pointing `DATABASE_URL` at the `athar_app` role — one line, reversible the same way. *Consequences:* a query that forgets to scope itself returns zero rows instead of another tenant's data, proved against a real restricted role in `tests/rls.test.ts`; the system escape is a short, greppable allowlist that mirrors the lint rule's; the cost is one transaction per façade call, paid only when enforcement is on; and this does **not** defend against an attacker who can already run arbitrary SQL as the app, which no same-role mechanism can.

**ADR-012 Team seats: three roles, one matrix, links instead of email.** *Context:* multi-brand already worked, but a database index enforced exactly one user per workspace — so an agency could not put a second person in it, and the "agency" plan sold to a market that could not use it collaboratively. *Options:* one unique index per (user, org) alone (rejected — it breaks the bootstrap race that keeps a user from silently owning two workspaces) · roles checked ad hoc at each call site (rejected — authorization scattered across twenty server actions is authorization nobody can audit, and it fails silently) · **a partial unique index plus a single capability matrix.** *Decision:* **`memberships_user_org_uq` on (user_id, org_id) for identity, and `memberships_owner_uq` on user_id WHERE role = 'owner' to keep the one-owned-workspace invariant that the bootstrap race depends on; three roles — owner, editor, reviewer — with every permission in one table in `lib/auth/roles.ts`, read through `requireCap()` in every guarded action.** Ownership is never invitable: it carries billing and erasure, and is transferred deliberately rather than granted by an email link. Invitations store only a SHA-256 of a 32-byte token and are redeemable **only by the invited address**, so a forwarded link is not a credential. *Consequences:* an agency can seat a writer and give their end client a review-only seat; a new capability is one row in one table rather than a hunt through call sites; an unknown role string reads as the most restricted role, never as more power than intended; the product does **not** send the invitation email — it returns a link the owner sends, because outbound mail is not configured and an invitation that silently fails to arrive is worse than none.

**ADR-013 The client review link is a capability, not an account.** *Context:* an agency's end client has to approve posts, and making them create an account to click "yes" loses the review cycle — but a workspace is full of things a client must never see. *Options:* a read-only guest seat (rejected — it is still a sign-up, and a seat that can be widened later is a seat that will be) · emailing a PDF of the month (rejected — the answers come back as prose someone has to transcribe, which is where approvals go to die) · **a bearer-token URL scoped to one brand's review queue.** *Decision:* **`review_links` grants exactly one capability — see this brand's reviewable posts, and set one of two statuses on them — and never becomes a session.** The module reads a fixed column set from one table for one brand in one state set within a 60-day window, and writes only `approved` or `needs_edit`; work in progress and decisions already taken are not shown at all. Tokens are stored as SHA-256, expire in 90 days, are revocable, and both the read and the write are rate-limited per IP. *Consequences:* a client reviews a month of posts in ten minutes with no account; a leaked link exposes one brand's queue for one cycle and is revoked in one click rather than being an account compromise; the note comes back attributed to the link, so Approvals shows who said it; and the narrowness is enforced by the query itself, not by a UI that happens not to render the rest.
